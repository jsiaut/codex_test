 CONSTATS PRIORITAIRES · 1/2


 Installation et temps historique
 F01 · P1 · Installation incomplète : 24 tests échouent dans un
 environnement neuf
 Preuve : Reproduit. Avec Python 3.12.14 et les six dépendances exactes de requirements.txt, la suite
 donne 24 échecs et 113 succès. Les échecs observés viennent de numpy absent lors de la création de la
 fonction DuckDB precision_radius. Les chemins utilisant fetchdf() nécessitent aussi pandas ; la
 restitution de timestamps avec fuseau dépend de pytz dans cet environnement.

 Conséquence : Un clone et la commande d’installation documentée ne suffisent pas. Un
 environnement personnel déjà enrichi masque facilement ce problème ; une réinstallation peut donc
 casser un projet qui fonctionnait auparavant.

 Correction minimale : Déclarer numpy, pandas et pytz, ou retirer réellement les usages qui les
 nécessitent. Documenter la version Python testée. Les versions effectivement utilisées pour cet audit
 sont numpy 2.5.4, pandas 3.0.6 et pytz 2026.5 ; ce sont des versions vérifiées ici, pas une obligation de
 mise à jour globale.

 Vérification ciblée : Après ajout de ces dépendances, les 137 tests passent. La dernière extension se régénère également
 à l’identique.

 Code figé : requirements.txt:1-6 ; secfragility/database.py:87-109 ; secfragility/targeted_priorities.py:60-62

 F02 · P1 · Le fuseau horaire peut changer un résultat historique
 Preuve : Reproduit sur un cas minimal. quarter_series.prepare convertit knowledge_date, une DATE, en
 TIMESTAMPTZ sans fixer le fuseau de la connexion. database.create laisse le fuseau implicite. Dans une
 fixture contenant deux dépôts, les mêmes faits donnent un revenu as_known de 1 000 000 en UTC et 2
 000 000 en America/New_York : le second dépôt devient admissible parce que la coupure absolue a
 changé.

 Conséquence : Changer de machine ou de configuration horaire peut changer la photographie
 historique. Les 137 tests passent pourtant dans les deux environnements : le test existant vérifie
 surtout la date civile et ne couvre pas ce cas de frontière.

 Correction minimale : Choisir explicitement la convention de publication et la fixer dans chaque
 connexion de calcul et de validation. Si la convention attendue est UTC, exécuter SET TimeZone='UTC'
 dans create et les autres connecteurs directs. Si une date SEC locale est voulue, la convertir
 explicitement dans cette zone, puis stocker l’instant UTC.

 Vérification ciblée : Conserver un test de frontière avec deux publications le même jour et comparer l’instant de coupure
 ainsi que la valeur sous UTC, Europe/Paris et America/New_York.

 Code figé : secfragility/database.py:87-94 ; secfragility/quarter_series.py:31-37 ; tests/test_publication_snapshot.py:10-39

 Validation et conservation du dernier résultat
 F03 · P1 · Les extensions échappent à la validation globale finale
 Preuve : Anomalie présente dans les tables. phase3.finish appelle verify_delivery avant les extensions
 SoftBank, Dell, SMCI et priorities. L’extension ciblée réutilise une entité existante par son nom sans
 vérifier son statut. Deux arêtes monétaires aboutissent ainsi à CoreWeave Financing DDTL V, LLC, qui
 n’a aucune version confirmed dans entities.

 Conséquence : Le résultat final viole no_pending_amount_edges, une règle que le projet impose
 lui-même. Les montants concernés sont 806 571 USD, côté BlackRock, et 5 319 000 USD, côté Ares, au
 30 juin 2026. Leur valeur source n’est pas mise en cause par ce constat ; c’est la qualification de leur
 destinataire qui reste incohérente.

 Correction minimale : Ajouter un contrôle global après toutes les extensions, juste avant la
 publication définitive. Dans entity(), traiter explicitement un nom déjà connu mais pending : confirmer
 l’identité juridique avec une preuve datée, sans inventer une consolidation au groupe, ou conserver
 l’observation sans arête monétaire admissible.

 Vérification ciblée : La requête exacte du contrôle no_pending_amount_edges doit renvoyer zéro sur les huit tables finales.
 Vérifier aussi que les cas existants et les nouvelles entités passent par le même garde-fou.

 Code figé : secfragility/phase3.py:118-149 ; secfragility/targeted_priorities.py:134-146 ;
 secfragility/targeted_priorities.py:190-202 ; secfragility/verify_delivery.py:15

 F04 · P1 · Une interruption peut laisser des tables de générations
 différentes
 Preuve : Reproduit par injection d’une erreur locale. database.export écrit les huit nouveaux fichiers
 dans un répertoire temporaire, puis remplace les anciens un par un. Une erreur simulée au
 remplacement de entities.parquet laisse documents, facts et observations nouveaux, avec les cinq
 autres tables anciennes. De plus, rebuild publie des tables intermédiaires dans tables/ avant la fin des
 calculs.

 Conséquence : Un arrêt, une erreur disque ou un échec tardif d’extension peut dégrader le dernier jeu
 exploitable. Une transaction DuckDB ne rend pas atomique cette série de remplacements de fichiers. Le
 statut validated_ready_for_final_commit est aussi écrit avant la fin des extensions.

 Correction minimale : Calculer et vérifier dans un nouveau dossier de résultats. Garder le dernier
 dossier validé intact jusqu’à la fin, puis changer un petit manifeste current.json qui indique le jeu à lire.
 Pour un usage manuel, un dossier daté validé et une étape explicite de sélection suffisent. Écrire le
 statut completed seulement à la toute fin.

 Vérification ciblée : Une erreur volontaire au milieu du calcul ou de l’export doit laisser le jeu précédent entièrement lisible
 et désigné comme courant.

 REPRISE ET ATTRIBUTION


 Deux garde-fous qui acceptent trop
 F05 · P2 · La reprise d’un checkpoint ignore les modifications de code
 Preuve : Reproduit. assembly_checkpoint.inputs calcule les empreintes du schéma, de la configuration,
 des requêtes et de certaines décisions. Il ne prend pas en compte secfragility/*.py. Modifier le code de
 calcul laisse donc inchangée la signature utilisée par resume pour accepter le checkpoint.

 Conséquence : Après une correction, --resume peut réutiliser des résultats calculés avec l’ancien
 algorithme et exécuter la suite avec le nouveau. Ce mélange est difficile à voir et peut donner
 l’impression que la correction n’a aucun effet.

 Correction minimale : Ajouter les empreintes des modules de calcul et des entrées effectivement
 consommées par l’étape sauvegardée. Une solution simple pour ce dépôt est un hash déterministe de
 secfragility/*.py, des fichiers SQL et de la configuration, plus les versions des dépendances de calcul.

 Vérification ciblée : Le changement d’un module qui influence le calcul doit refuser la reprise et demander une
 reconstruction. La modification d’une simple note documentaire ne doit pas obliger à tout recalculer.

 Code figé : secfragility/assembly_checkpoint.py:7-31

 F06 · P2 · La présence du nom dans le bloc ne prouve pas son lien avec
 le montant
 Preuve : Contre-exemple accepté par le validateur. validate_semantics exige que la citation soit
 présente dans le bloc et que la contrepartie nommée figure quelque part dans ce bloc. Ces conditions
 sont indépendantes. Le bloc « We paid OpenAI $100. We paid Anthropic $200. » accepte une
 observation citant la première phrase, montant 100 USD, contrepartie Anthropic.

 Conséquence : Une erreur d’annotation humaine peut passer tous ces contrôles de présence et
 affecter le graphe. La sélection ciblée utilise parfois le document entier comme bloc, ce qui élargit la
 surface de cette confusion. Aucune attribution fausse déjà publiée n’est démontrée par cette fixture.

 Correction minimale : Pour une attribution directe, exiger la contrepartie dans la citation exacte du
 montant et vérifier la ligne ou le contexte choisi. Pour une attribution par renvoi documentaire, imposer
 une preuve de liaison séparée et explicite. Éviter de faire porter au seul nom trouvé dans un grand bloc
 une garantie sémantique qu’il ne fournit pas.

 Vérification ciblée : Le contre-exemple fourni doit être rejeté. Les renvois documentaires légitimes doivent rester possibles
 avec leur preuve distincte.

 Code figé : secfragility/observations.py:15-56 ; secfragility/targeted_priorities.py:95-116

 Relier la preuve au résultat réellement produit
 F09 · P2 · Les preuves de tests ne sont pas rattachées au code
 réellement empaqueté
 Preuve : Défaut établi par lecture du code. targeted_package lit des booléens enregistrés dans
 replay_verification.json, puis calcule les empreintes du code actuel. Il ne compare pas ces empreintes à
 celles du code réellement testé. Les nombres full_tests_passed=137 et isolated_tests_passed=5 sont
 écrits en dur. Comparer le contenu du ZIP au code courant prouve la copie, pas l’exécution antérieure
 des tests sur ce code.

 Conséquence : Après une modification locale, un ancien fichier de preuve peut encore autoriser un
 paquet qui se présente comme testé. Le rejeu indépendant réalisé pendant cet audit confirme bien
 l’état actuel ; le défaut concerne la fiabilité de la prochaine attestation.

 Correction minimale : Enregistrer les empreintes des fichiers et le résultat réel de la commande au
 moment du test ou du rejeu. Refuser l’empaquetage si le code ou les entrées ont changé. Remplacer les
 compteurs constants par les valeurs de cette exécution.

 Vérification ciblée : Changer un module après le rejeu doit invalider la preuve jusqu’à une nouvelle vérification. Il n’est pas
 nécessaire d’ajouter un service externe pour cela.

 Code figé : secfragility/targeted_package.py:22-27 ; secfragility/targeted_package.py:34-50

 F10 · P3 · 255 lignes de ratios portent une devise monétaire
 Preuve : Incohérence de métadonnées présente. 251 lignes SoftBank et quatre lignes CRWV ont
 unit=ratio avec currency non nulle. Plusieurs appels SoftBank passent explicitement currency=JPY pour
 des ratios ; le ratio de liquidité borné CRWV conserve USD. La règle est déjà correctement appliquée
 aux ratios de la dernière extension.

 Conséquence : La valeur du ratio n’est pas rendue fausse par cette étiquette. En revanche, un export,
 un formatteur ou un futur calcul générique peut le traiter comme un montant monétaire. Le schéma
 devient moins uniforme.

 Correction minimale : Mettre currency à NULL pour les résultats sans dimension. Garder la devise des
 termes dans les faits de provenance, où elle reste nécessaire pour vérifier leur compatibilité. Appliquer
 la même règle aux ratios bornés et aux lignes sans valeur.

 Vérification ciblée : La requête unit='ratio' AND currency IS NOT NULL doit renvoyer zéro après harmonisation.

 Code figé : secfragility/softbank_integration.py:277-310 ; secfragility/softbank_integration.py:488 ;

 Chemins, sessions et effets de bord
 F11 · P3 · Certains chemins empêchent une utilisation locale portable
 Preuve : Constaté dans les points d’entrée. Les paquetages SoftBank et Dell utilisent un chemin absolu

 prouvent pas cette portabilité.

 Correction minimale : Utiliser un dossier output/ relatif au projet, et un argument --output pour les
 paquetages. Résoudre les chemins de lecture à partir du root transmis. Charger les vues propres aux
 extensions quand leurs sources sont disponibles.

 Vérification ciblée : Le même point d’entrée doit fonctionner depuis la racine et avec un root explicite depuis un autre
 répertoire. La génération locale d’un paquet doit pouvoir choisir un dossier accessible.

 F12 · P3 · Le verrou réseau est contrôlé après l’envoi de la requête
 Preuve : Reproduit avec un transport simulé. SecClient.get appelle le transport puis _journal, qui
 appelle enfin lock.touch. Si le verrou appartient déjà à une autre session, une requête est tout de même
 envoyée avant l’erreur. Le contre-exemple fourni compte un appel simulé avant « Le verrou de cette
 session a été perdu ».

 Conséquence : Le cas se produit surtout lors d’une session devenue obsolète ou de deux lancements
 locaux. Le verrou ne garantit alors plus strictement qu’un seul processus accède au réseau. Aucun
 dépassement n’a été trouvé dans le journal historique contrôlé.

 Correction minimale : Vérifier et rafraîchir le verrou juste avant chaque appel au transport, y compris
 après une attente et avant une nouvelle tentative. La correction est locale au client existant.

 Vérification ciblée : Avec un jeton de verrou incorrect, le transport simulé doit compter zéro appel. Conserver le contrôle
 du verrou au moment du journal également.
